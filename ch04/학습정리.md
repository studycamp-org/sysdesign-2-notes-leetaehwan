# 분산 메시지 큐: 소비와 안전한 처리

## 1. 풀과 롱 폴링

**풀(pull)**은 소비자가 브로커에 메시지를 요청하는 방식이다. 소비자는 자신의 처리 여건에 맞춰 다음 요청 시점과 한 번에 가져올 양을 조절할 수 있다.

**롱 폴링(long polling)**은 풀 요청을 받았을 때 즉시 전달할 메시지가 없으면, 브로커가 일정 시간 기다렸다가 메시지가 도착하거나 대기 시간이 끝났을 때 응답하는 방식이다. 빈 요청을 자주 반복하지 않으면서 새 메시지에도 빠르게 반응할 수 있다.

롱 폴링은 메시지가 생기면 기다리던 소비자에게 응답한다는 점에서 푸시와 비슷해 보인다. 차이는 소비자가 요청을 시작하고 다음 요청 시점을 정한다는 것이다. 다만 푸시 방식에서도 소비자의 처리 능력을 고려해 전송량을 제한할 수 있다.

풀을 사용해도 처리 속도가 자동으로 조절되는 것은 아니다. 한 번에 너무 많은 메시지를 가져오면 소비자 내부에 처리 대기 메시지가 쌓일 수 있으므로, 가져오는 양과 작업 대기열 크기를 함께 관리해야 한다.

## 2. 소비자 그룹과 파티션

소비자 그룹은 같은 목적의 소비자들이 파티션을 나눠 처리하는 단위다. 그룹마다 독립적인 오프셋을 관리하므로 같은 이벤트를 각 그룹이 독립적으로 읽을 수 있다.

```text
주문 이벤트 ─┬─ 결제 그룹 → 결제 처리
             ├─ 배송 그룹 → 배송 처리
             └─ 정산 그룹 → 정산 처리
```

그룹이 독립적이므로 결제 그룹이 늦어져도 다른 그룹의 읽기 위치가 함께 밀리지는 않는다. 다만 **업무 처리 순서는 자동으로 보장되지 않는다**. 배송이 결제 승인을 기다려야 한다면, 승인 완료 이벤트를 받는 등 업무 흐름에서 그 관계를 표현해야 한다.

같은 그룹에서는 일반적으로 한 파티션을 한 소비자에게 배정한다. 이를 통해 파티션 안의 순서를 관리하기 쉽고, 여러 소비자가 같은 파티션을 동시에 처리하는 상황을 피한다.

```text
파티션 0 → 소비자 A
파티션 1 → 소비자 B
파티션 2 → 소비자 C
```

파티션이 3개라면 그룹에서 동시에 일하는 소비자는 최대 3명이다. 네 번째 소비자는 대기하다가 다른 소비자가 빠지면 파티션을 넘겨받을 수 있다.

## 3. 재조정과 중복 처리

소비자가 추가되거나 장애로 빠지면 그룹은 파티션을 다시 배정한다. 이를 **재조정(rebalancing)**이라고 한다. 이때 영향을 받는 파티션의 처리가 잠시 멈출 수 있다.

새 소비자는 그룹이 마지막으로 커밋한 위치부터 이어 읽는다. 기존 소비자가 메시지를 처리했지만 그 결과를 커밋하기 전에 종료됐다면, 새 소비자가 해당 메시지를 다시 처리할 수 있다.

따라서 파티션을 한 소비자에게만 배정해도 **장애와 재조정으로 인한 중복 처리는 발생할 수 있다**.

## 4. 병렬 처리와 안전한 오프셋 커밋

처리량을 높이기 위해 한 소비자가 서로 다른 주문을 병렬로 처리할 수 있다. 같은 주문 ID의 메시지는 순서대로 처리하고, 서로 다른 주문은 별도 작업자에게 맡기는 방식이다.

```text
파티션 → 소비자 ─┬─ 작업자 1: 주문 A 순차 처리
                 ├─ 작업자 2: 주문 B 순차 처리
                 └─ 작업자 3: 주문 C 순차 처리
```

병렬 처리에서는 메시지의 **완료 순서가 읽은 순서와 달라질 수 있다**.

| 오프셋 | 상태 |
|---|---|
| 98 | 완료 |
| 99 | 처리 중 |
| 100 | 완료 |

이때 100번까지 완료한 것으로 커밋하면, 장애 후 아직 처리 중이던 99번을 건너뛸 수 있다. 따라서 **앞에서부터 빈틈없이 처리 완료된 위치까지만 커밋**한다.

```text
98번 완료 · 99번 처리 중 · 100번 완료
→ 98번까지 처리 완료

이후 99번 완료
→ 100번까지 처리 완료
```

Kafka의 커밋 오프셋은 보통 *다음에 읽을 위치*를 뜻한다. 따라서 위에서 98번까지 완료했다면 **99**를, 100번까지 완료했다면 **101**을 커밋한다.

구현할 때는 자동 커밋을 끄고, 파티션별로 실제 읽은 메시지의 순서와 완료 상태를 추적한다. 작업이 밀리면 읽기를 일시 중지해 대기열이 무한히 커지지 않도록 한다. 재조정 시에는 완료된 위치까지만 커밋하고, 미완료 작업은 재전달될 수 있다고 가정한다.

안전하게 커밋해도 중복은 남는다. 위 예에서 99번이 처리 중일 때 장애가 나면, 이미 완료한 100번도 다시 읽을 수 있다. 이를 다루는 것이 멱등 처리다.

## 5. 결제의 멱등 처리

**멱등 처리**는 같은 요청을 여러 번 수행하더라도 실제 효과가 한 번만 발생하도록 하는 것이다. 안전결제에서는 같은 결제 시도가 재전달돼도 고객이 두 번 결제되지 않아야 한다.

결제 시도마다 고유한 `payment_attempt_id`를 만들고, 같은 시도의 재시도에는 항상 같은 ID를 PG 멱등성 키로 사용한다.

```text
주문 123의 첫 결제 시도 → P001
P001의 재전송          → 같은 키 P001
사용자의 새 결제 시도  → 새로운 키 P002
```

주문 ID만 사용하면 같은 주문의 정상적인 새 결제 시도까지 이전 요청으로 취급될 수 있다. 반대로 재시도할 때마다 새 키를 만들면 PG가 서로 다른 결제로 인식할 수 있다.

처리 흐름은 다음과 같다.

1. 결제 시도 ID와 요청 내용을 영속 저장하고, ID에 고유 제약을 둔다.
2. 해당 ID를 멱등성 키로 PG에 결제를 요청한다.
3. 확인한 결제 결과를 DB에 저장한다.
4. 메시지를 처리 완료로 표시하고, 파티션에서 빈틈없이 완료된 위치까지 오프셋을 커밋한다.

### PG 승인 직후 장애가 난다면

```text
① PG 결제 승인 성공
② DB에 승인 결과를 저장하기 전 소비자 장애
③ 메시지 재전달
```

DB에 승인 결과가 없더라도 PG에서는 결제가 성공했을 수 있다. 새 키로 다시 요청하면 중복 결제될 수 있으므로, **기존 결제 시도 ID**로 PG 결과를 조회하거나 PG의 보장 조건 안에서 같은 키로 재시도한다. 결과를 확인해 DB에 저장한 뒤 메시지 처리를 완료한다.

실제 구현에서는 PG의 멱등성 키 보관 기간, 중복 요청 처리 방식, 결과 조회 방법을 확인해야 한다. PG가 필요한 보장을 제공하지 않는 경우에는 거래 조회와 대사 등 별도 복구 절차가 필요하다.

## 6. 파티션 쏠림과 느린 소비자 대응

지연이 늘면 먼저 파티션별 **유입 속도와 처리 속도**를 비교한다.

| 원인 | 대응 방향 |
|---|---|
| 여러 주문이 특정 파티션에 집중 | 키 분포와 파티션 설계를 살펴보고 부하 분산 검토 |
| 주문 하나에 이벤트가 집중 | 중복 이벤트·재시도 확인. 키를 쪼개면 주문별 순서 보장이 어려워짐 |
| 특정 소비자만 느림 | 해당 인스턴스의 자원, 네트워크, 오류와 재시도 확인 |
| PG 응답이 전반적으로 느림 | PG 응답 시간·호출 한도와 타임아웃·재시도 정책 확인 |
| 서로 다른 주문을 순차 처리해 대기 | 주문별 순서는 유지하면서 서로 다른 주문을 병렬 처리 |

이미 파티션마다 소비자가 하나씩 배정됐다면 소비자를 더 추가해도 남는 소비자는 대기한다. 또한 파티션 수를 변경하면 기존 주문 키가 다른 파티션으로 이동할 수 있으므로, 주문별 순서를 지키기 위한 전환 계획이 필요하다.
